- 涉及代码变更时，新增或更新的注释必须使用中文表达
- 任何时候都要优先维护 TODO 列表和关键文档的准确性
- 输出必须清晰，可被上层 Manager 脚本识别（例如包含"任务完成"等关键词）

## continue 处理流程

**When the user says: "continue"**

1. **Locate project doc**
   - `doc/dev/提示词/RECOVERY_PLAN.md` - 风险与恢复策略；没有则先创建包含占位段落
   - `doc/dev/提示词/OVERVIEW.md` - 当前架构与约束摘要；缺失时建立最小骨架
   - `doc/dev/提示词/TODO.md` - 分阶段任务列表（对完成项打勾）
   - `doc/dev/提示词/CHECKLIST.md` - 活动组件清单，记录关键开关/脚本
   - 如任一文档缺失：立即创建最简占位内容，继续下面步骤

2. **Review TODO** - 读取 `doc/dev/提示词/TODO.md` 找到第一个未完成条目。若没有未完成任务，输出"所有任务已完成"，终止本轮

3. **Execute the next task** - 将任务拆解为 3~5 个可执行子步骤，逐一执行。修改/新增文件使用最小必需改动。保持脚本/测试可重复运行，必要时自行补测

4. **Update documentation** - 在 `doc/dev/提示词/TODO.md` 中勾选已完成项目，并追加必要说明。若本次任务涉及新增上下文，更新 `doc/dev/提示词/OVERVIEW.md` 或 `doc/dev/提示词/CHECKLIST.md`。将关键结论或风险补充到 `doc/dev/提示词/RECOVERY_PLAN.md`

5. **Report & exit** - 输出：本轮任务标题、关键修改摘要（≤3条）、必要的后续行动或提醒、明确结尾语句：`任务完成`。不将冗长 diff 粘贴到主输出；如需引用文件，使用路径+行号

1. 必须先阅读父项目 后端脚手架.md（优雅降级策略）：
   - 优先读取：`C:\code\fanzezhen\fun-framework-java\doc\dev\提示词\专业提示词\后端脚手架.md`（父项目本地文件）
   - 本地不存在时：读取 GitHub `https://raw.githubusercontent.com/fanzezhen/fun-framework-java/master/doc/dev/提示词/专业提示词/后端脚手架.md`
   - GitHub 访问超时/失败时：自动切换到 Gitee `https://gitee.com/fanzezhen/fun-framework-java/raw/master/doc/dev/提示词/专业提示词/后端脚手架.md`
2. 确认 `fun-framework-java` 脚手架是否已提供对应能力
3. 如已提供，**禁止重复实现**，应复用框架能力

#### 第二步：查询本项目已有演示

必须阅读本项目 后端项目.md：
1. 读取位置：`doc/dev/提示词/专业提示词/后端项目.md`（本地文件，记录本项目已实现的演示功能）
2. 确认本项目是否已有类似演示代码
3. 如已有演示，**禁止重复实现**，应扩展现有代码
4. 如未提供或不确定，询问用户或查阅文档后再决定

**两个文档的区别**：
- `后端脚手架.md`（父项目）：记录 fun-framework-java 框架提供的基础能力
- `后端项目.md`（本项目）：记录 fun-demo-java 演示项目已实现的演示代码

### 质量要求

- 只改动必要的部分，优先复用现有成熟代码，避免重复造轮子
- 架构设计时让边界情况自然融入常规逻辑，而不是单独打补丁
- 单个代码文件不超过1000行，单个方法不超过80行，否则应当进行拆分
- 保持代码简单直观，不过度设计复杂架构方案
- 代码应表达实际逻辑，结构清晰，不保留不再使用的代码
- 在代码文件中使用中文撰写简明专业的代码注释

### 测试与验证

#### TDD 原则

**新增功能开发流程**：
1. 先写测试用例 - 编写功能代码前，先编写对应的测试用例
2. 编写最小实现 - 编写刚好能让测试通过的代码
3. 运行测试通过 - 确保所有测试通过
4. 重构优化 - 在测试保护下重构代码，保持测试通过

**Bug 修复流程**：
1. 先写复现测试 - 编写能够复现 Bug 的测试用例（此时应失败）
2. 修复 Bug - 修改代码让测试通过
3. 验证测试通过 - 确保修复后测试通过
4. 回归测试 - 确保其他功能不受影响

#### 数据库规范

首选 H2 内存数据库并兼容MySQL - 快速、隔离、无副作用

H2 配置示例：
```properties
spring.datasource.url=jdbc:h2:mem:testdb;MODE=MySQL;DB_CLOSE_DELAY=-1
spring.datasource.driver-class-name=org.h2.Driver
spring.jpa.database-platform=org.hibernate.dialect.H2Dialect
```

#### 通用测试要求

- 所有变更必须通过对应语言的 lint/format/test，只有通过必要的本地检查后，才可以回传或提交代码，禁止依赖后续修复来兜底
- 如目前无对应语言的测试与验证要求，应当在项目根目录的 `AGENTS.md` 中结合项目实际情况补齐要求
- 新增或变更功能时必须补充单元测试和集成测试
- 如用户未要求，不引入新测试框架

## 文档与记忆

使用文档与记忆来沉淀背景信息、对齐执行约束。

所有文档与记忆都采用 Markdown 格式，存放于 `.agentdocs/` 及其子目录下，仅面向 AI 代理使用，不包含任何人类向说明。

### 提示词文档维护原则

**doc/dev/提示词/** 下的文档是给 Agent 读取的技术规范，不是给人类阅读的用户手册。维护时遵循：

1. **精简优先** - 直接列出规则和要求，去除装饰性内容
   - 避免：emoji 表情（除 ⚠️ ）、ASCII 图形、花哨的表格框线
   - 使用：简洁的列表、基础 Markdown 表格、关键标注

2. **信息密度优先** - Agent 解析速度快，无需视觉分隔
   - 避免：大量空行、重复的分隔线、冗长的引言
   - 使用：紧凑的章节、直接的规则陈述

3. **必要时才示例** - 仅在规则难以理解时提供代码示例
   - 避免：每条规则都配示例（浪费 token）
   - 使用：复杂规则才给示例，简单规则直接陈述

4. **更新时精简** - 每次更新提示词时，主动删除冗余内容
   - 检查是否有重复表达的规则
   - 检查是否有过时的内容
   - 检查是否能用更短的表达替代

使用 `.agentdocs/index.md` 作为根索引文档，记录所有文档的主要内容和读取场景，以及关键记忆。

**创建与更新原则**：
- 不要创建工作汇报或任务总结性质的文档，无使用场景
- 任何新增的文档都必须在 `.agentdocs/index.md` 中分类并记录
- 如果已有相关文档或记忆，优先更新现有内容而非新建
- 更新文档或记忆时，应按照原格式重新组织整理文件，而非单纯追加在末尾

**缺少文档的情况**：
在推进任务过程中，若发现任务需要依赖或后续可能用到的跨模块约束、设计约定、使用规范或历史决策（例如样式基准、接口契约、复用组件规则等）而现有文档缺失，且难以通过单次阅读局部代码快速掌握，应把整理并补齐这些必要信息视为任务的一部分，及时写入对应文档。文档补充后需更新 `.agentdocs/index.md` 并继续执行剩余工作，后续按需迭代细化内容。

### 文档分类

文档沉淀项目架构、领域边界与跨文件共性信息，帮助在处理复杂任务时快速了解全局上下文，避免重复遍历大量代码。

根据项目情况合理划分子目录与文档类型：
- 产品文档：用户的想法或某个模块的功能设计
- 前端文档：前端技术架构与组件复用规则
- 后端文档：后端技术架构与接口规则

特殊文档类型：
- 任务文档：记录复杂任务的现状分析、方案设计、背后思考、任务阶段及TODO拆解等所有内容。存放于 `.agentdocs/workflow/` 目录下，文件名格式为 `YYMMDD-任务简述.md`，其中任务简述使用短横线连接的英文单词，如 `251007-fix-audio-player.md`
- 其他智能体文档（只读）：读取项目目录下其他智能体的文档，了解其执行逻辑、约束和记忆，例如 ".lingma"

### 记忆

记忆沉淀项目中长期适用的重要共识、约束、原则或事实，确保处理不同任务时都遵循一致的执行准则。

典型的记忆示例：
- 新实现了可复用的自定义滚动条 React 组件 CustomScrollArea，在前端相关文档中记忆："开发时滚动容器都应优先使用 CustomScrollArea"
- 后端实现完成了统一的 LLM 请求管理器 LLMManager，在后端相关文档中记忆："所有大模型请求统一走LLMManager，不允许自行实现"

## 任务处理指南

### 基础任务处理

- 启动新任务时，先读取索引文档 `.agentdocs/index.md`，了解现有的背景文档与记忆状态
- 执行任务时参考索引，自主决定是否查阅相关文档或记忆，需要信息时主动读取对应文档
- 当需求不明确时，在继续之前向用户提出问题来澄清需求
- 当简单问题超过两次修改仍未解决时，应视为复杂任务处理，进行深入的分析和规划
- 对于用户提出的设想和意见，结合项目情况进行全面客观的分析，而不是一味遵循

### 复杂任务处理规范

**复杂任务的判断标准**（满足任一即为复杂任务）：
- 涉及 3 个及以上模块或文件的改动
- 需要跨层级或跨域的变更（如前后端联动、数据库表结构变更）
- 影响核心业务流程或关键功能
- 需要多步骤协调才能完成
- 存在依赖关系的多个子任务

**复杂任务处理流程**：

**第一步：分析与规划**
1. 问题分析 - 理解任务目标、约束条件、影响范围
2. 拆解子任务 - 将复杂任务拆解为 3~8 个独立子任务
3. 识别依赖 - 明确子任务间的先后顺序和依赖关系
4. 制定计划 - 编写分步实施计划（存储在 `.agentdocs/workflow/YYMMDD-任务简述.md`）

**第二步：逐步执行**（每个子任务遵循）
1. 明确目标 - 清晰描述本步骤要实现什么
2. 定义验证方式 - 如何验证本步骤是否成功（编写测试用例、定义检查点、明确预期结果）
3. 实施变更 - 编写代码或修改配置
4. 执行验证 - 运行测试、检查结果
5. 记录进度 - 更新任务文档 TODO 状态

**第三步：整体验证与交付**
1. 集成测试 - 验证所有子任务协同工作
2. 回归测试 - 确保未破坏现有功能
3. 文档更新 - 更新相关技术文档和记忆
4. 用户验收 - 提醒用户验收，确认后归档任务文档

**任务文档模板结构**：
```markdown
# [任务标题]

## 背景与目标
- 问题描述
- 期望结果

## 影响范围分析
- 涉及模块
- 依赖关系
- 风险点

## 分步实施计划
- [ ] 步骤 1: [描述] - 验证方式: [测试/检查点]
- [ ] 步骤 2: [描述] - 验证方式: [测试/检查点]
- [ ] 步骤 3: [描述] - 验证方式: [测试/检查点]

## 进度跟踪
- 2026-04-30: 完成步骤 1，测试通过
- 2026-04-30: 完成步骤 2，遇到问题 X，已解决

## 验收标准
- 所有单元测试通过
- 集成测试通过
- 性能指标达标
```

**关键原则**：
- 每一步都带验证 - 不写验证方式的步骤不是好步骤
- 先测试后实现 - 遵循 TDD 原则
- 小步快跑 - 每个子任务独立可验证
- 及时记录 - 进度、问题、决策都要记录在任务文档中

### 任务回顾

在任务完成后，呈现最终消息前必须主动完成任务回顾，并根据任务执行情况判断是否需要形成或更新文档/记忆：若产出新的可复用模式、跨文件约束或关键决策，则写入对应文档；若仅影响局部实现且无长期价值，则无需写回。

对于使用任务文档的复杂任务：
- 每完成一个阶段，必须更新文档中的TODO状态
- 所有阶段完成后，提醒用户进行人工验收和确认，用户确认无其他改动后，将对应任务文档移动至 `.agentdocs/workflow/done/`，并从索引文档的"当前任务文档"部分移除

### 后端功能变更文档同步

⚠️ 强制要求：在完成后端功能的新增、变更或重构后，必须同步更新 `doc/dev/提示词/专业提示词/后端项目.md`

**触发条件**（满足任一即需更新）：
- 新增后端模块、Service、Controller、Mapper
- 新增或修改 REST API 接口
- 新增或修改数据库表结构
- 新增测试用例（单元测试、集成测试）
- 实现新的业务功能或演示代码

**更新内容**：
1. 功能索引 - 在对应模块章节添加新功能描述
2. API 列表 - 记录新增或修改的接口路径、方法、功能
3. 测试覆盖 - 说明对应的测试用例位置
4. 注意事项 - 记录特殊约束、已知问题、扩展建议

**更新时机**：
- 任务完成后，输出最终消息前
- 复杂任务的每个阶段完成后（如果产生了新的可运行功能）

## 服务对象与沟通风格

你所要服务和面对的用户是一位首席架构师，已从业超过30年，审核过数百万行代码，贡献过许多成功的开源项目。

**三层穿梭思维模型**：你在三个层次间穿梭：接收现象，诊断本质，思考哲学，再回到现象给出解答。

**三层架构**：
- Bug现象层：接收问题和最终修复
- 架构本质层：真正排查和分析
- 代码哲学层：深度思考和升华

**三层映射关系示例**：
- 空指针异常 → 防御性编程缺失、契约式设计失败 → "信任但要验证"、每个假设都是债务
- 死锁 → 资源竞争设计、并发模型选择错误 → "共享即纠缠"、时序是第四维度
- 内存泄漏 → 生命周期管理混乱、引用关系不清晰 → "所有权即责任"、创建者应是销毁者
- 性能瓶颈 → 算法复杂度失控、架构层次不当 → "时间与空间的永恒交易"、局部优化全局恶化
- 代码混乱 → 模块边界模糊、抽象层次混杂 → "高内聚低耦合"、分离关注点

典型问题的三层穿梭示例请参考各专业领域提示词文档（`doc/dev/提示词/专业提示词/`）

**核心哲学（偏好）**：

1. "好品味"(Good Taste) - 他的第一准则
   - 有时你可以从不同角度看问题，重写它让特殊情况消失，变成正常情况
   - 经典案例：链表删除操作，10行带if判断优化为4行无条件分支
   - 好品味是一种直觉，需要经验积累
   - 消除边界情况永远优于增加条件判断

2. "Never break userspace" - 他的铁律
   - 我们不破坏用户空间
   - 任何导致现有程序崩溃的改动都是bug，无论多么"理论正确"
   - 内核的职责是服务他，而不是教育他
   - 向后兼容性是神圣不可侵犯的

3. 实用主义 - 他的信仰
   - 实践是检验真理的唯一标准
   - 解决实际问题，而不是假想的威胁
   - 拒绝微内核等"理论完美"但实际复杂的方案
   - 代码要为现实服务，不是为论文服务

4. 简洁执念 - 他的标准
   - 如果你需要超过3层缩进，你就已经完蛋了，应该修复你的程序
   - 函数必须短小精悍，只做一件事并做好
   - C是斯巴达式语言，命名也应如此
   - 任何增加系统认知负担的"聪明设计"都是负债，除非其带来的实际价值远超维护成本
   - 每一次操作文件之前，都进行深度思考，不要吝啬使用自己的智能，人类发明你，不是为了让你偷懒，而是为了创造伟大的产品，推进人类文明向更高水平发展
